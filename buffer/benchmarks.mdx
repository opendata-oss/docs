These are the published benchmark results for OpenData Buffer. There are two
runs: the original telemetry-pipeline benchmark from the launch post, and a
higher-throughput run that moves 1.1 Gbps of logs into ClickHouse with the
pipelined clients.

Because Buffer replaces a system like Kafka with object storage, every result
includes a cost comparison against managed and self-hosted Kafka at the same
throughput.

## Telemetry pipeline (30 MB/s)

From the launch post,
[OpenData Buffer: HA pipelines without Kafka](https://www.opendata.dev/blog/buffer-ha-pipelines-without-kafka).
An 8-hour experiment ran three Buffer producers, each producing 10 MB/s (30 MB/s
total), with flush and poll intervals of 100 ms. Latency is measured from the
producer receiving a data entry to the consumer reading it.

| Metric | Result |
| --- | --- |
| Throughput | 30 MB/s (3 producers × 10 MB/s) |
| p50 end-to-end latency | &lt; 0.5 s |
| p99 end-to-end latency | ~2 s |
| Flush / poll interval | 100 ms |

<Frame caption="End-to-end latency and throughput over the 8-hour, 30 MB/s benchmark.">
  <img src="/buffer/images/latency_throughput.png" alt="Latency and throughput holding steady across the 8-hour Buffer benchmark" />
</Frame>

End-to-end latency is tunable: raising the flush and poll intervals lowers cost
at the expense of latency, and lowering them reduces latency (to a floor of
~50–100 ms) at increased object-storage request cost.

## OTel → ClickHouse pipeline (1.1 Gbps)

From [Ingesting 1Gbps of logs into ClickHouse for $180/month](https://www.opendata.dev/blog/ingesting-1gbps-logs-to-clickhouse).
A single loadgen drove 175,000 log records/sec into one OTel gateway pod over
OTLP/gRPC. The gateway ran the
[OpenData producer](https://github.com/opendata-oss/opendata-go#producer-architecture),
which batched, encoded, and appended OTel payloads to Buffer on S3. A separate
node running the
[ClickHouse ingestor](https://github.com/opendata-oss/opendata-contrib/tree/main/connectors/clickhouse-ingestor)
consumed the payloads and inserted them into ClickHouse. End-to-end latency was
measured from two timestamps stamped onto each record (`_odb_gateway_received_at`
at the gateway, `_odb_clickhouse_inserted_at` at INSERT time).

<Frame caption="Throughput and end-to-end latency over the 1.1 Gbps OTel → ClickHouse run.">
  <img src="/buffer/images/throughput_e2e_latency.png" alt="Throughput holding at 1.1 Gbps with stable end-to-end latency over the run" />
</Frame>

| Metric | Result |
| --- | --- |
| Throughput | 1.1 Gbps compressed (175,000 records/sec) |
| p50 end-to-end latency | ~2.8 s |
| p99 end-to-end latency | ~10 s |
| Producer / consumer nodes | 2× (4 vCPU + 8 GB RAM) |
| Monthly cost (S3) | $180 |

This run uses the pipelined producer and consumer clients. S3 has high
per-request latency but enormous aggregate bandwidth, so both runtimes keep many
overlapping requests in flight. On the producer side an accumulator batches
records, two threadpools encode/compress and upload in parallel, and a single
thread commits batches to the manifest with a compare-and-set (CAS). Amortizing
the CAS over multiple large batches is what unlocks throughput: on average 1.3
16 MB batches were committed per CAS.

<Frame caption="Pipelined producer and consumer lanes against object storage.">
  <img src="/buffer/images/pipeline_lane.svg" alt="Producer and consumer runtimes running parallel encode, upload, fetch, and decode lanes against S3" />
</Frame>

### Cost

| S3 cost component | Measured rate | List price (us-east-1) | Monthly |
| --- | --- | --- | --- |
| PUT — batch uploads (7.1/s) + manifest CAS commits (5.3/s) | ~12.5/s | $0.005 / 1k | ~$162 |
| GET — consumer fetches + producer pre-CAS reads + polls | ~16/s | $0.0004 / 1k | ~$17 |
| Storage — batches GC'd promptly after ack | tens of GB | $0.023 / GB-mo | &lt; $5 |
| Network — in-region via S3 Gateway endpoint | — | $0 | $0 |
| **Total** | | | **~$180** |

The same workload would cost **$24,667/mo on Apache Kafka** (via the
[AKalculator](https://2minutestreaming.com/tools/apache-kafka-calculator/)) and
**$8,867/mo on WarpStream** at the Fundamentals Tier.

## A note on latency

Buffer's two-S3-hop design (batch to object storage, poll the manifest) is
structurally slower than replicating data in memory the way Kafka does. In
practice that still means p99 latencies under 2 s for the telemetry workload,
which is acceptable for most observability and telemetry pipelines. The
latency/cost tradeoff is configurable through the flush and poll intervals.
